# Принять новую версию шаблона

**Когда:** «обнови метод», «вышла новая версия шаблона», «подтяни шаблон».

**Что меняется.** Только **файлы метода** — список в `../structure.md`
§Файлы метода. Всё остальное — дело владельца (его домены, решения,
preferences, owner) — не трогается: новая версия меняет метод, а не
написанные файлы. Привести файлы к новому методу — отдельный шаг, по слову.

## Шаги

1. **Откуда.** Remote `template` (после сборки так переименован `origin`
   шаблона). Нет — ⏸ владелец: `git remote add template
   https://github.com/skandar11/llm-wiki.git`. Новый шаблон пришёл папкой
   (флешка, архив, без сети) — читать журнал и брать файлы метода из неё,
   шаги те же; без git у базы — сначала `git init` и коммит «до приёма».
2. `git fetch template`. Прочитать в `template/main:meta-vault/vault-template.md`
   §Журнал формы **только строки новее** версии из `../structure.md` — это
   единственное место, где сказано, что изменилось по существу.
3. ⏸ владелец: пересказать изменения и спросить, принимаем ли.
4. Записать, от чего уходим: старая версия — строкой в `../structure.md`
   §Журнал сборки.
5. Заменить файлы метода: `git checkout template/main -- <пути из списка>`.
   Не трогать ничего вне списка.
6. **Сверить каждое изменённое правило с базой — открыв файлы.** Для каждого:
   база уже так / база иначе. Иначе → два законных исхода: привести (по
   слову владельца) **или** записать строку в `../structure.md`
   §Расхождения с причиной. **Третьего нет** — молчаливое расхождение рождает
   две редакции одного правила.
7. Новая версия — в `../structure.md`. Прогон
   [[check-links-and-names|проверки]]: формы могли переименоваться. Коммит.

**Важно.** Расхождение с шаблоном само по себе не дефект — живая база в своём
случае обычно права. Дефект — незаписанное расхождение.
