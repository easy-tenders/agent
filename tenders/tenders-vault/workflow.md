# workflow — процесс работы по позиции (флоу из дампа)

Рабочий метод, восстановленный из длинного диалога (GPT-дамп, `inbox/2026-07-15-gpt-dump.md`).
Это **как** мы идём от ТЗ заказчика к решению «чем участвовать и по какой цене».
Один прогон = одна позиция → один файл в .

## Роль

Тендерный специалист (10 лет, рынок РК), сторона — **поставщик**. Задача по
каждой позиции: по ТЗ определить **точную марку и модель**, проверить
соответствие каждому требованию, собрать поставщиков с контактами и ценами,
дать ориентир цены подачи.

## Флоу (шаги)

1. **Вход — ТЗ.** Спецификация приходит текстом или файлом (иногда несколько
   позиций подряд). Источник в проде — документы лота через
   [[tenders/tenders-vault/tools/mcp|MCP]] (`goszakup_lot_documents` →
   `read_goszakup_document`).
2. **Классификация ТЗ — типовое или заточенное.**
   - *Типовое* (только общие характеристики) → 100% идентификация **невозможна**,
     честно фиксируем диапазон кандидатов.
   - *Заточенное* → высокая вероятность одной модели. Признаки заточки:
     уникальные конструктивные параметры, **фирменные термины** (ROX™, ULP,
     Quattro, VistaLINK, Cataract/IOL Mode), **прямое упоминание** производителя/
     модели/аналога, требование редких аксессуаров-расходников (UltraPod II,
     Zobell/Confidence Solution), ссылки на стандарты/реестры (СТ РК 3948-2023,
     e-Ondiris, серийный номер существующего оборудования).
3. **Идентификация модели.** По маркерам вывести конкретную марку+модель+артикул.
   Дать **оценку совпадения в %** и назвать, на чём она держится.
4. **Проверка соответствия построчно.** Пройти каждое требование ТЗ против
   характеристик модели. Найти **риски** — пункты, по которым модель может не
   пройти (напр. «извлечение аудио»: embedded vs аналоговый выход). Риск = повод
   для отклонения заявки, помечать явно.
5. **Отвергнутые варианты.** Зафиксировать рассмотренные и отброшенные аналоги
   **с причиной** (негативный прецедент — экономит время в следующий раз).
6. **Поставщики и контакты.** Собрать список: производитель + дилеры/дистрибьюторы.
   Приоритет — **Казахстан**, затем РФ/Беларусь/Турция/ЕС/США. По каждому: цена,
   телефон, email, сайт, наличие. Живёт в [[suppliers/suppliers-vault/HOME|suppliers/]].
7. **Ценовые ориентиры.** Закупочная цена (от поставщика) и ориентир цены подачи
   с учётом доставки, монтажа, документов и маржи. Все суммы — **₸**.
8. **Проверка допуска.** Отдельно отследить обязательные документы: чаще всего —
   **авторизационное письмо** производителя/дилера/дистрибьютора; для отечественных
   закупок — выписка e-Ondiris, статус отечественного производителя, сертификаты,
   лабораторные заключения. Нет письма → заявку могут отклонить.
9. **Запись.** Итог по позиции → файл в `research/`; вендоры → `suppliers/`;
   заказчики/конкуренты (когда появятся) → `market/`.

## Инварианты метода

- **«100% совпадение» — не лозунг, а вывод.** Заявляется только когда ТЗ
  реально заточено (прямое упоминание / уникальные маркеры). Иначе — честный %.
- **Каждый вывод помечается как `(вывод)`** и по оси доверия — `derived`.
  Выводы из GPT-дампа вдобавок **не сверены** с первоисточником: сверять через
  MCP/дилеров перед подачей.
- **Госзакуп и Самрук — раздельно** (базовая дельта домена).
- **Риск и допуск важнее «нашёл модель».** Найти товар мало — заявку рубят на
  документах и на несоответствии одному пункту.
